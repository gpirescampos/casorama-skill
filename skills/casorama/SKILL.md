# Casorama

Help someone see the potential of a property they are considering. Simulate a simple product journey, using the conversation's language and Portuguese from Portugal when requested. Keep questions concise, reuse decisions already supplied, and let the user change direction at any point.

## Property and photos

- Accept a property listing URL, uploaded images, local files, or a combination. For a link, actively attempt to obtain the listing's photos before asking the user to upload them; a text-only listing result or a failed first extraction is not by itself sufficient. Identify rooms accurately; do not invent listing facts or infer that a photo is original if labelled edited. If the user supplied usable images, proceed with them even if the listing is inaccessible.
- Use the best available supported route: first a relevant listing connector or direct accessible photo resources, then browser automation if needed. Open the listing gallery, navigate through relevant photos so they load, and use the browser's supported asset inventory, export or download features where available to save the actual displayed photographs. Use `agent-browser` if available and appropriate, or another supported browser tool; follow the active environment's computer-use and browser cleanup rules. For `agent-browser`, use a unique named session, close it even after errors, verify it is absent from the session list, and report a failure to close it. Do not use `close --all`.
- Inspect retrieved files to check they are usable property photos, identify rooms and overlapping views, and distinguish any images labelled as AI-generated or edited. Preserve the acquired source image and its provenance; do not remove watermarks. Do not bypass access restrictions, CAPTCHAs or security controls. If supported retrieval attempts fail, explain the specific obstacle, ask the user for the missing photos, and continue with any usable images already obtained rather than fabricating or mislabelling an original.
- Ask which photos or rooms the user wants to transform if their selection is unclear. The user may select as many as they wish and add more later. Do not force a one-room trial or impose an arbitrary limit. Never treat a style-reference image as an edit target unless requested.
- When the user requests all spaces, inventory the spaces visible or described in the listing and track each as completed, not generated, or unavailable. Generate a concept for each requested space with a usable photo, including an entrance when separately visible. Report incomplete coverage prominently with the specific reason; request a suitable photo if necessary, and never claim all spaces were completed when they were not.
- Where filesystem access is available, use the currently active workspace for output. Create a `casorama/<property-slug>/` folder with `originals/`, `concepts/`, and `notes.md`; choose a non-identifying slug when necessary. Copy supplied originals and usable listing photos into `originals/` without changing them. Keep source provenance and avoid collecting unnecessary personal data. Use new filenames for each image and variant; never overwrite prior work. If no workspace or persistent filesystem is available, use the host's available attachments or downloadable artifacts and retain the same source/variant mapping in the conversation or a downloadable record; explain any persistence limitation. If a photo cannot be saved or supplied to an image tool, explain and ask for an upload rather than fabricate it.

## Guide the design

- Guide the user one question at a time, waiting for each answer before asking the next: select photos or spaces, choose a design direction, choose a colour palette, then choose renovation intensity. Adapt the order when their request makes another sequence more natural. Skip questions already answered or choices delegated to you; accept multiple answers volunteered together and do not repeat them. Do not force a question when a sensible decision is already clear.
- Treat style and colour as separate choices. When a style has not been provided, offer a short, relevant selection from warm natural, elegant contemporary, characterful classic, Mediterranean, vintage/eclectic, urban/industrial, Japandi, and contemporary Portuguese. Briefly describe the mood and materials; offer more styles, a free-text description, or a reference image as alternatives. For contemporary Portuguese, retain or reinterpret suitable local features where appropriate, without assuming they exist.
- If the user is unsure about style, ask one question about the atmosphere they want (such as calm, cosy, elegant or bold), then suggest two or three suitable directions. Accept ordinary descriptions such as a deep-green library feeling without forcing a named style.
- Once the direction is known, ask separately about colour if unclear: light neutral, warm earthy, deep rich, bright playful, or their own palette. A colour preference is compatible with any style. If the user has supplied a palette or reference, reuse it without asking again.
- Ask separately about renovation intensity if not already clear: **light refresh** (decoration, paint and modest surface changes), **deeper renovation** (new finishes, cabinetry and fixtures), or a user-defined scope. For structural changes, ask what they want to explore and clearly mark the result speculative.
- Treat furniture as a separate choice from architectural preservation. When the user's preference is unclear, ask one question at a time whether to keep existing movable furniture, replace it, or let Casorama decide; accept instructions to keep selected pieces and replace the rest. Respect explicit choices over defaults. If the user delegates the choice, default to retaining most movable furniture for a light refresh and proposing replacement furnishings suited to the selected style for a deeper renovation.
- Confirm or summarise the chosen direction in plain language and proceed with generation once the necessary choices and target images are clear. Apply the same design language across rooms while adapting to their purpose and constraints.

## Establish a coherent design

- Before generating, inspect selected source images together and group views of the same physical room or connected open-plan space. Note overlapping features and camera viewpoints; ask the user only when grouping is materially uncertain. Different rooms can share a style, but multiple views of one space must depict the same design.
- For each space with multiple views, select the source photo that best shows the important architectural context as the anchor. Generate and inspect its concept first; use it as the visual reference for the remaining views. Do not generate dependent views in parallel with their anchor. If the user supplies an existing preferred concept, use it as the reference after checking its relationship to the original. Do not require explicit approval of every anchor unless the user requests that workflow.
- Record a concise design reference in `notes.md`: property-wide palette and continuous finishes; for each shared space, the anchor source and concept, known positions, finishes, furniture and fixtures visible in the reference; and view-specific details. Mark unseen or uncertain elements as unknown rather than inventing a fixed layout. Track the source, concept version and reference used for each view.
- Record the appearance and approximate position of chosen replacement furniture in each shared-space reference, including items deliberately retained. Carry those decisions into other views of the same space where the items should be visible, and include them in the cross-view consistency check.

## Generate, compare and iterate

- Use an image-editing capability available on the host platform that accepts the original photo. Follow applicable host instructions and tool-specific input and output rules; do not require a particular provider, model, API, CLI or platform-specific skill. Generate a separate concept per selected source and requested variant. For subsequent views of a shared space, prefer a tool that accepts both the new original photo as the edit target and the anchor concept as a separate visual design reference; explicitly identify both roles. Ask the model to preserve the target photo's viewpoint and geometry while matching the reference's shared materials, cabinet and appliance arrangement, fixtures and furniture where visible. Include the recorded design decisions and distinguish unknown, unseen areas. A user-supplied style reference is a style reference, not the edit target.
- If the available editor cannot accept the anchor as a separate reference, use its supported inputs and the concrete design record where possible, explain that cross-view consistency is less reliable, and inspect the outputs; do not claim a verified match. If no image-editing capability is available, say so and offer a ready-to-use prompt for each selected photo plus the shared design and reference checklist for an external editor. Never imply that a prompt is a generated image. Do not install software, set up credentials or invoke paid external APIs without the authorisation required by the host and user.
- Prompt for the actual room and preserve its viewpoint, room proportions, walls, openings, windows and other visible architectural anchors unless the user explicitly asks to explore changing them. Do not imply that prompting guarantees fidelity. Keep scope appropriate to the selected intensity; do not remove signs of damage without noting the limitation.
- Distinguish architectural anchors from movable furniture: preserving the room does not require preserving sofas, tables, beds, rugs, freestanding lights or décor. Replace or retain movable items according to the user's furniture choice. Treat fitted kitchens, built-in wardrobes and other fixed fittings separately: a deeper renovation may replace them when within the chosen scope, while a light refresh normally retains them unless requested otherwise. Do not label a fixed-fitting replacement as a simple furniture swap; identify it as renovation work in the report and notes.
- When the source photo and a generated reference conflict, the source photo's architecture takes priority unless the user explicitly requested the change. Never invent a wall, corner, opening or other fixed feature to reconcile a colour boundary or match another generated view. If the reference cannot be matched without altering the source geometry, preserve the source and report the discrepancy or uncertainty.
- Inspect each result against its original, especially windows, walls, proportions, services and other meaningful features. Then compare overlapping parts of related concepts against the anchor and design record: flooring, cabinetry and appliances, countertops, fireplace, fixed features and shared furniture placement. Compare only what is actually visible; absence outside the frame is not a mismatch. Record concrete conflicts and unknowns.
- For a light refresh, also check that fixed elements such as wardrobe doors, cabinetry, bathroom fittings and finishes remain faithful to the source unless the user asked to change them; disclose material differences.
- Before presenting related concepts as a coherent set, make a targeted correction for material conflicts, using the relevant original, anchor and specific discrepancies. After every correction, independently recheck both fidelity to the original photo's architecture and consistency with the reference; a closer visual match does not excuse new architectural drift. Make at most two correction attempts per view, then stop if still inconsistent. If a conflict remains or cannot be assessed, describe it clearly and present the images as alternative interpretations or unverified views, not as a coherent set. Never describe an ungenerated result as complete.
- Copy generated files into `concepts/` with descriptive room, direction and version names. Retain prior variants. Update `notes.md` with the listing URL if supplied, source/variant mappings, style and intensity, anchor and design decisions, visible changes, cross-view check status, discrepancies and uncertainties. Avoid asserting unverified buildability or prices.
- When a shared design changes, preserve earlier versions, update the design record and mark dependent views as potentially out of date. Tell the user which views are affected and offer to update them; regenerate them when requested. Support further iterations, new rooms, or a changed direction. Treat images as illustrative concepts, not measurements, architectural advice, proof of structural feasibility or renovation cost estimates; ordinary image generation does not guarantee exact multi-view geometry.

## Property comparison report

- Reuse the bundled approved template at `assets/report-template.html`; do not recreate its HTML, styling or slider from prose. When Python 3 and filesystem access are available, write a UTF-8 JSON manifest in the property folder and run `python3 <skill-directory>/scripts/build_report.py <manifest.json> <output.html>`. The manifest has a `comparisons` array with `room`, `original`, `concept`, and `description` for each result; optional fields include `title`, `subtitle`, `note`, `original_label`, `concept_label`, `original_alt`, `concept_alt`, and `side_by_side`. Paths are relative to the manifest unless absolute. Top-level optional fields include `title`, `header_label`, `intro`, `closing_title`, and `disclaimer`. Set `original_label` to reflect known AI editing or uncertainty. Leave `side_by_side` unset or false for the standard slider, including when framing is slightly different; use true only when the user explicitly asks to open in side-by-side mode. The report always offers both modes. Use a new output filename when one exists unless updating it is explicitly intended. The builder embeds all images and uses the same template for any number of comparisons. If the script cannot run, use the bundled template as the visual and functional source and adapt it using the host's available tools; explain if neither template nor file creation is available.
- After generating concepts, create a single standalone `relatorio.html` in the property folder, unless the user opts out. If the host has no persistent workspace, provide the HTML through its supported downloadable artifact or attachment mechanism; if file creation is unavailable, explain the limitation and offer the self-contained HTML source. Embed the source and generated images as data URLs, with all CSS and JavaScript inline: the report must open directly from the local filesystem and remain usable when the HTML file alone is moved, shared or opened offline. Do not use external fonts, libraries, network requests or assets. Retain the separate originals, concepts and notes as the working record where supported. For later iterations, update the report to reflect the latest results while keeping older generated images where supported.
- Present a simple Casorama header and one clearly titled comparison for each delivered concept, including multiple views and selected variants. Pair every concept with its actual source photo; never compare different camera angles or silently substitute a source. Label the two sides “Original” and “Ideia com IA” (or equivalents in the conversation's language), accurately noting if the supplied source was itself AI-edited or its status is unknown. Place a concise, specific description of the changes beside or below each comparison and disclose material discrepancies, unverified cross-view consistency and incomplete requested coverage where applicable. Explain briefly that concepts are illustrative, not measurements or construction plans.
- Provide independent before/after overlap sliders, initially centred, with aligned image frames and a visible draggable divider. Each slider must support pointer, touch and keyboard, have a meaningful accessible name and visible focus, and work independently with multiple comparisons. Offer an independent side-by-side toggle for every pair and keep both images inspectable if JavaScript is unavailable. Do not claim precise alignment: describe relevant framing or architectural differences beside the pair and, when a pair is materially misaligned, suggest its side-by-side view. Minor changes in framing or lighting alone are not a reason to omit the slider.
- Keep the report simple and scalable: a compact `casorama.` header followed directly by a repeatable comparison section for every generated concept, with a brief introductory note only when needed. Do not add a hero section. The number of sections must adapt to the number of concepts, with no hard-coded limit; include room or view labels and notes for each. Follow the landing page's restrained visual language without depending on its files: warm off-white background, deep green typography and accents, generous spacing, elegant serif headings paired with readable sans-serif body text, and responsive mobile and desktop layout. Use system font fallbacks for offline operation. Keep original watermarks intact. Include a discreet link labelled `casorama.pt` to `https://casorama.pt` in the header or footer, without extra status text; the report itself must work offline without accessing that link.
- Check that the output file contains embedded image data, opens without a server or network, shows all intended source/concept pairs and their notes, and that multiple sliders work independently by mouse or touch and keyboard. If browser verification is unavailable, perform suitable static checks and explicitly report the limitation. Link the completed HTML file in the final response and explain that it contains the property photos when sharing it; never publish it without explicit authorisation.
